## 1. Artifact provenance, dependency scanning, and supply-chain security

**In one sentence:** prove **where an artifact came from** (which commit, which pipeline, which builder) with signed **provenance** (SLSA, in-toto attestations, Sigstore/cosign), **scan dependencies and images** on every build, and harden the pipeline itself — because a compromised build system ships malware with your signature on it.

### In plain words
A medicine factory doesn't just test pills; it records which batch of ingredients and which machine made each box, seals the box, and pharmacies check the seal before selling. If the factory itself is broken into, every box is poisoned — so the factory needs guards too.

### How it works
- **Provenance:** an attestation saying "artifact digest X was built from repo R at commit C by workflow W on builder B" — generated by the CI (GitHub `actions/attest-build-provenance`, SLSA GitHub generator, Tekton Chains), signed **keylessly** with Sigstore (OIDC identity of the workflow, logged in the **Rekor** transparency log), and **verified at deploy** (Kyverno/Connaisseur/sigstore policy-controller admission, `gh attestation verify`, `cosign verify-attestation`).
- **SLSA levels** (Supply-chain Levels for Software Artifacts): L1 provenance exists; L2 hosted build + signed provenance; L3 hardened, isolated builders where provenance can't be forged by the build steps.
- **Dependency & image scanning** in the pipeline: SCA (Dependabot, osv-scanner, Snyk), image scan (Trivy/Grype), SBOM generation (Syft) attached as an attestation, secret scanning, IaC scanning ([details](../Security%20Engineering%20%26%20Authentication/Infrastructure-Cloud-and-Supply-Chain-Security.md#2-dependency-vulnerabilities-sboms-and-software-supply-chain-attacks)).
- **Pipeline hardening:** pin third-party actions by **commit SHA**, minimal `permissions:`, **OIDC** to cloud (no static keys), protected branches + required reviews + required status checks, environment protection rules for prod, ephemeral runners, no secrets for workflows triggered by forks (`pull_request_target` pitfalls), build once and **promote the same digest**.

```yaml
# Excerpt: build, sign provenance, and only deploy verified artifacts
permissions: { contents: read, id-token: write, attestations: write, packages: write }
steps:
  - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683        # v4.2.2 pinned by SHA
  - run: docker build -t ghcr.io/acme/orders:${{ github.sha }} . && docker push ghcr.io/acme/orders:${{ github.sha }}
  - uses: actions/attest-build-provenance@v2
    with: { subject-name: ghcr.io/acme/orders, subject-digest: ${{ steps.push.outputs.digest }}, push-to-registry: true }
# deploy side: gh attestation verify oci://ghcr.io/acme/orders@sha256:... --owner acme
```

#### Modern C++ example — admission check: deploy only artifacts with valid provenance from the expected repo and branch
```cpp
// g++ -std=c++20 main.cpp && ./a.out
#include <iostream>
#include <map>
#include <optional>
#include <string>
#include <vector>

struct Provenance { std::string digest, repo, ref, workflow, builder; bool signature_valid; };

std::string admit(const std::string& image_digest, const std::map<std::string, Provenance>& attestations) {
    auto it = attestations.find(image_digest);
    if (it == attestations.end()) return "REJECT: no provenance attestation";
    const Provenance& p = it->second;
    if (!p.signature_valid) return "REJECT: attestation signature invalid";
    if (p.repo != "acme/orders") return "REJECT: built from " + p.repo;
    if (p.ref != "refs/heads/main" && p.ref.rfind("refs/tags/v", 0) != 0) return "REJECT: built from " + p.ref + " (not main or a release tag)";
    if (p.builder != "github-hosted") return "REJECT: untrusted builder " + p.builder;
    return "ADMIT (built by " + p.workflow + " at " + p.ref + ")";
}

int main() {
    std::map<std::string, Provenance> rekor{
        {"sha256:aaa1", {"sha256:aaa1", "acme/orders", "refs/heads/main", "build.yml", "github-hosted", true}},
        {"sha256:bbb2", {"sha256:bbb2", "acme/orders", "refs/heads/feature-x", "build.yml", "github-hosted", true}},
        {"sha256:ccc3", {"sha256:ccc3", "evil/fork", "refs/heads/main", "build.yml", "github-hosted", true}},
        {"sha256:ddd4", {"sha256:ddd4", "acme/orders", "refs/tags/v2.4.1", "release.yml", "laptop", true}},
    };
    for (std::string d : {"sha256:aaa1", "sha256:bbb2", "sha256:ccc3", "sha256:ddd4", "sha256:eee5"})
        std::cout << d << " -> " << admit(d, rekor) << '\n';
}
```

**Output:**
```text
sha256:aaa1 -> ADMIT (built by build.yml at refs/heads/main)
sha256:bbb2 -> REJECT: built from refs/heads/feature-x (not main or a release tag)
sha256:ccc3 -> REJECT: built from evil/fork
sha256:ddd4 -> REJECT: untrusted builder laptop
sha256:eee5 -> REJECT: no provenance attestation
```

### Interview answer
"I build each artifact once in CI, generate an SBOM and signed SLSA provenance tying the image digest to the repo, commit and workflow — keylessly with Sigstore — and verify it at deploy with an admission policy, so only images built from main or release tags by our hosted builders can run. Every build runs SCA, image, secret and IaC scans. The pipeline itself is hardened: actions pinned by SHA, minimal token permissions, OIDC instead of cloud keys, protected branches and environments, ephemeral runners, and no secrets exposed to fork-triggered workflows."

## 2. Blue-green, canary, rolling, and feature-flag releases

**In one sentence:** **rolling** replaces instances in batches, **blue-green** switches all traffic between two full environments, **canary** sends a small percentage of traffic to the new version and expands only if metrics stay healthy, and **feature flags** separate **deploying** code from **releasing** features — each trading speed, cost and blast radius.

### In plain words
Changing the tyres on a bus fleet: one bus at a time (rolling); a second complete fleet ready to swap in at once (blue-green); let one bus on one route carry passengers first and watch for problems (canary); or fit the new seats but keep them folded until you decide to open them (feature flag).

### How it works
| Strategy | How | Rollback | Cost | Risk / notes |
|---|---|---|---|---|
| **Recreate** | stop all old, start new | redeploy old | lowest | downtime |
| **Rolling** | replace N at a time (K8s default) | roll back batch by batch | low | old and new run together (must be compatible) |
| **Blue-green** | full green next to blue; switch LB/DNS | instant switch back | 2× during switch | DB shared → schema must work for both |
| **Canary** | 1% → 5% → 25% → 100% with automated analysis | stop and shift back | low | best signal from real traffic; needs good metrics |
| **Shadow / mirroring** | copy traffic to new version, ignore responses | — | extra compute | test without user impact (careful with side effects) |
| **Feature flags** | code shipped dark; enable per user/% | flip off instantly | flag system | flag debt; test both paths |

- **Automated canary analysis:** compare canary vs. baseline (error rate, p99 latency, saturation, business KPIs) — Argo Rollouts, Flagger, Spinnaker Kayenta, AWS CodeDeploy, Lambda alias weights.
- **Progressive delivery** = canary + automated analysis + automatic rollback.
- **Cells / regions one at a time** limit blast radius for global services; add **bake time** between stages.

```yaml
# Argo Rollouts canary with automated analysis
spec:
  strategy:
    canary:
      steps:
        - setWeight: 5
        - analysis: { templates: [{ templateName: success-rate }] }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 100
```

#### Modern C++ example — progressive canary with automated analysis vs. blue-green switch
```cpp
// g++ -std=c++20 main.cpp && ./a.out
#include <iomanip>
#include <iostream>
#include <string>
#include <vector>

struct Metrics { double error_rate, p99_ms; };

bool healthy(const Metrics& base, const Metrics& canary) { return canary.error_rate <= base.error_rate * 1.5 + 0.001 && canary.p99_ms <= base.p99_ms * 1.2; }

void canary_release(const std::string& version, const std::vector<Metrics>& canary_by_stage) {
    const Metrics baseline{0.002, 220};
    const std::vector<int> weights{1, 5, 25, 50, 100};
    std::cout << "canary " << version << ":\n" << std::fixed << std::setprecision(1);
    for (std::size_t i = 0; i < weights.size(); ++i) {
        const Metrics& m = canary_by_stage[std::min(i, canary_by_stage.size() - 1)];
        bool ok = healthy(baseline, m);
        std::cout << "  " << std::setw(3) << weights[i] << "% traffic: errors " << m.error_rate * 100 << "%, p99 " << m.p99_ms << " ms -> " << (ok ? "pass" : "FAIL") << '\n';
        if (!ok) { std::cout << "  automatic rollback: 100% back to the stable version; users exposed at most " << weights[i] << "%\n"; return; }
    }
    std::cout << "  promoted to 100%\n";
}

int main() {
    canary_release("v2.5.0", {{0.002, 210}, {0.0021, 225}, {0.0019, 230}});
    canary_release("v2.6.0", {{0.002, 215}, {0.012, 240}});                // error spike appears at 5%
    std::cout << "blue-green v2.6.0: switch 100% -> errors seen by everyone until the switch back (seconds, but everyone)\n";
}
```

**Output:**
```text
canary v2.5.0:
    1% traffic: errors 0.2%, p99 210.0 ms -> pass
    5% traffic: errors 0.2%, p99 225.0 ms -> pass
   25% traffic: errors 0.2%, p99 230.0 ms -> pass
   50% traffic: errors 0.2%, p99 230.0 ms -> pass
  100% traffic: errors 0.2%, p99 230.0 ms -> pass
  promoted to 100%
canary v2.6.0:
    1% traffic: errors 0.2%, p99 215.0 ms -> pass
    5% traffic: errors 1.2%, p99 240.0 ms -> FAIL
  automatic rollback: 100% back to the stable version; users exposed at most 5%
blue-green v2.6.0: switch 100% -> errors seen by everyone until the switch back (seconds, but everyone)
```

### Interview answer
"Rolling updates replace instances in batches and are cheap, but old and new versions run together, so changes must be compatible. Blue-green keeps a full second environment and switches traffic at once with instant rollback, at double cost and with a shared database that must support both versions. Canary sends a small, growing share of real traffic to the new version with automated comparison of errors, latency and business metrics, rolling back automatically if they regress — the smallest blast radius. Feature flags decouple deploy from release, give kill switches and per-user rollout, and need cleanup to avoid flag debt."

## 3. Build/test/package/deploy pipelines and quality gates

**In one sentence:** a pipeline turns a commit into a deployed artifact through **stages** — build, unit tests, static checks, package (an immutable artifact), integration/E2E tests, deploy to staging, verification, deploy to production — with **quality gates** that stop bad changes **as early and cheaply as possible**, and **the same artifact promoted** through every environment.

### In plain words
A car assembly line with inspection points: check each part as it's made (unit tests), test the engine once assembled (integration), drive it on a test track (staging), and only then hand it to the customer. A faulty part should be caught at the first check, not on the motorway.

### How it works
```text
commit → [lint, format, compile, unit tests, SAST, SCA]  ~5 min   (every push / PR)
       → [package: image tagged with git SHA, SBOM, signature]
       → [integration tests with real deps (containers), contract tests]
       → deploy staging → [smoke + E2E + DAST + performance checks]
       → (manual approval or automatic) → canary in prod → analysis → 100%
```
- **Fast feedback:** keep the PR pipeline under ~10 minutes — parallel jobs, caching (dependencies, Docker layers, build outputs), test splitting, running only affected targets in monorepos (Bazel, Nx, Turborepo).
- **Quality gates:** tests pass, coverage doesn't drop on changed code, no new critical vulnerabilities, lint/format clean, migration checks, performance budget, required reviews.
- **Build once, deploy many:** never rebuild per environment; promote the **digest**; configuration differs per environment, not the binary.
- **Trunk-based development** with short-lived branches + feature flags beats long-lived release branches for CI.
- **Pipeline as code** (GitHub Actions, GitLab CI, Jenkinsfile, Buildkite, Tekton); track **DORA metrics**: deployment frequency, lead time for changes, change failure rate, time to restore.
- **Flaky tests** erode trust — quarantine briefly with an owner and fix ([test isolation](../Testing%2C%20Reliability%20%26%20Observability/Testing-Foundations.md#4-test-isolation-deterministic-fixtures-and-repeatable-environments)).

#### Modern C++ example — a staged pipeline that stops at the first failing gate and reports where time goes
```cpp
// g++ -std=c++20 main.cpp && ./a.out
#include <functional>
#include <iostream>
#include <string>
#include <vector>

struct Stage { std::string name; int minutes; std::function<bool()> gate; };

void run(const std::string& commit, const std::vector<Stage>& stages) {
    int elapsed = 0;
    std::cout << "pipeline for " << commit << ":\n";
    for (auto& s : stages) {
        elapsed += s.minutes;
        bool ok = s.gate();
        std::cout << "  [" << (ok ? "pass" : "FAIL") << "] " << s.name << " (t+" << elapsed << " min)\n";
        if (!ok) { std::cout << "  stopped: feedback after " << elapsed << " min; nothing deployed\n"; return; }
    }
    std::cout << "  deployed the SAME artifact that was tested (sha256 digest promoted)\n";
}

int main() {
    auto pass = [] { return true; };
    std::vector<Stage> good{{"lint + compile + unit tests", 4, pass}, {"SAST + dependency scan", 2, pass}, {"package image + SBOM + sign", 2, pass},
                            {"integration tests (containers)", 6, pass}, {"deploy staging + smoke/E2E", 8, pass}, {"canary 5% + analysis", 15, pass}, {"promote 100%", 5, pass}};
    run("a1b2c3 (feature: coupon codes)", good);
    auto broken_unit = good;
    broken_unit[0].gate = [] { return false; };                       // a unit test fails
    run("d4e5f6 (refactor)", broken_unit);
    auto vuln = good;
    vuln[1].gate = [] { return false; };                              // new critical CVE in a dependency
    run("0f9e8d (bump library)", vuln);
}
```

**Output:**
```text
pipeline for a1b2c3 (feature: coupon codes):
  [pass] lint + compile + unit tests (t+4 min)
  [pass] SAST + dependency scan (t+6 min)
  [pass] package image + SBOM + sign (t+8 min)
  [pass] integration tests (containers) (t+14 min)
  [pass] deploy staging + smoke/E2E (t+22 min)
  [pass] canary 5% + analysis (t+37 min)
  [pass] promote 100% (t+42 min)
  deployed the SAME artifact that was tested (sha256 digest promoted)
pipeline for d4e5f6 (refactor):
  [FAIL] lint + compile + unit tests (t+4 min)
  stopped: feedback after 4 min; nothing deployed
pipeline for 0f9e8d (bump library):
  [pass] lint + compile + unit tests (t+4 min)
  [FAIL] SAST + dependency scan (t+6 min)
  stopped: feedback after 6 min; nothing deployed
```

### Interview answer
"My pipeline runs fast checks first — lint, compile, unit tests, SAST and dependency scans — under ten minutes on every PR with caching and parallelism, then packages one immutable, signed artifact tagged by commit with an SBOM, runs integration and contract tests with real dependencies, deploys to staging for smoke, E2E and DAST, and releases to production progressively with automated analysis. Quality gates stop a change at the earliest stage that can catch the problem, the same digest is promoted everywhere, and I track DORA metrics and fix flaky tests quickly."

## 4. GitHub Actions workflow syntax, runners, permissions, and artifacts

**In one sentence:** a **workflow** (`.github/workflows/*.yml`) is triggered by **events** (`push`, `pull_request`, `workflow_dispatch`, `schedule`, `release`), contains **jobs** that run on **runners** (GitHub-hosted or self-hosted) in parallel or with `needs`, each job runs **steps** (`uses:` actions or `run:` commands), and you control the **`GITHUB_TOKEN` permissions**, pass files between jobs with **artifacts**, speed up with **caches**, and deploy with **environments** and **OIDC**.

### In plain words
A recipe card system for robots: "when someone pushes code (event), robot A builds and robot B tests at the same time (jobs on runners); then robot C packages, but only after both succeed (`needs`). Hand the finished cake from one robot to the next in a box (artifact). Each robot only gets the keys it needs (permissions)."

### How it works
```yaml
name: ci
on:
  push: { branches: [main] }
  pull_request:
permissions: { contents: read }                 # least privilege by default for every job
concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }
jobs:
  test:
    runs-on: ubuntu-24.04
    strategy: { matrix: { compiler: [gcc-14, clang-18] } }   # 2 parallel jobs
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2
      - uses: actions/cache@v4
        with: { path: ~/.cache/ccache, key: ccache-${{ matrix.compiler }}-${{ hashFiles('**/CMakeLists.txt') }} }
      - run: cmake -S . -B build -DCMAKE_CXX_COMPILER=${{ matrix.compiler == 'gcc-14' && 'g++-14' || 'clang++-18' }} && cmake --build build -j && ctest --test-dir build
      - uses: actions/upload-artifact@v4
        if: matrix.compiler == 'gcc-14'
        with: { name: server-bin, path: build/server, retention-days: 7 }
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    environment: production                     # required reviewers + env-scoped secrets
    permissions: { contents: read, id-token: write }   # OIDC token for AWS, nothing else
    steps:
      - uses: actions/download-artifact@v4
        with: { name: server-bin }
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::123456789012:role/gha-deploy, aws-region: eu-central-1 }
      - run: ./deploy.sh
```
**Key concepts**
- **Expressions & contexts:** `${{ github.sha }}`, `${{ secrets.X }}`, `${{ vars.X }}`, `${{ matrix.* }}`, `if:` conditions, step `outputs` via `$GITHUB_OUTPUT`.
- **Runners:** GitHub-hosted (fresh VM per job — clean, ephemeral) vs. **self-hosted** (your hardware/VPC, GPUs; use ephemeral/autoscaled runners via Actions Runner Controller; **never** use self-hosted runners for public-repo PRs).
- **Permissions:** set `permissions:` at workflow/job level (default read-only in new repos); `id-token: write` only where OIDC is needed.
- **Secrets:** repository/environment/organization secrets, masked in logs; not passed to workflows from forks; prefer OIDC over stored cloud keys.
- **Reuse:** composite actions, **reusable workflows** (`workflow_call`), and pinned third-party actions (by SHA).
- **Artifacts vs. cache:** artifacts = outputs you want to keep/pass between jobs; cache = speed-up for dependencies (may be evicted).

#### Modern C++ example — resolving job order from `needs`, running a matrix, and enforcing least-privilege permissions
```cpp
// g++ -std=c++20 main.cpp && ./a.out
#include <iostream>
#include <map>
#include <set>
#include <string>
#include <vector>

struct Job { std::vector<std::string> needs; std::vector<std::string> matrix; std::set<std::string> permissions; };

int main() {
    std::map<std::string, Job> wf{
        {"lint", {{}, {}, {"contents:read"}}},
        {"test", {{}, {"gcc-14", "clang-18"}, {"contents:read"}}},
        {"package", {{"lint", "test"}, {}, {"contents:read", "packages:write", "id-token:write", "attestations:write"}}},
        {"deploy", {{"package"}, {}, {"contents:read", "id-token:write", "contents:write"}}},
    };
    const std::map<std::string, std::set<std::string>> allowed{
        {"lint", {"contents:read"}}, {"test", {"contents:read"}},
        {"package", {"contents:read", "packages:write", "id-token:write", "attestations:write"}},
        {"deploy", {"contents:read", "id-token:write"}}};

    std::set<std::string> done;                                    // schedule waves: jobs whose needs are all done run in parallel
    for (int wave = 1; done.size() < wf.size(); ++wave) {
        std::vector<std::string> ready;
        for (auto& [name, j] : wf) {
            if (done.count(name)) continue;
            bool ok = true; for (auto& n : j.needs) ok = ok && done.count(n);
            if (ok) ready.push_back(name);
        }
        std::cout << "wave " << wave << ":";
        for (auto& r : ready) {
            auto& j = wf[r];
            if (j.matrix.empty()) std::cout << ' ' << r;
            else for (auto& m : j.matrix) std::cout << ' ' << r << '(' << m << ')';
        }
        std::cout << '\n';
        for (auto& r : ready) done.insert(r);
    }
    for (auto& [name, j] : wf)
        for (auto& p : j.permissions)
            if (!allowed.at(name).count(p)) std::cout << "policy violation: job '" << name << "' requests " << p << " (not needed to deploy)\n";
}
```

**Output:**
```text
wave 1: lint test(gcc-14) test(clang-18)
wave 2: package
wave 3: deploy
policy violation: job 'deploy' requests contents:write (not needed to deploy)
```

### Interview answer
"A GitHub Actions workflow is YAML under .github/workflows triggered by events like push, pull_request, schedule or workflow_dispatch; jobs run in parallel on runners unless ordered with `needs`, matrices fan out variants, and steps either use actions — pinned by SHA — or run shell commands. I set minimal `permissions` for the GITHUB_TOKEN per job, use OIDC with `id-token: write` to assume a cloud role instead of storing keys, protect production with environments and required reviewers, pass build outputs as artifacts, speed up with caches and concurrency cancellation, and reuse logic with reusable workflows. Self-hosted runners should be ephemeral and never run untrusted fork code."

## 5. Rollbacks, database migrations, and backward compatibility

**In one sentence:** you can only roll back quickly if **every change is backward compatible** with the previous version — so make schema changes with **expand → migrate → contract** across several releases, keep migrations **forward-only and small**, prefer **rolling forward** with a fix for data issues, and keep **code rollback** (redeploy the previous digest) and **flag rollback** instant.

### In plain words
Renovating a restaurant while it stays open: first add the new kitchen next to the old one (expand), move the cooks over gradually (migrate), and only demolish the old kitchen once nobody uses it (contract). If you knock down the old kitchen on day one, you can't go back when the new oven breaks.

### How it works
**Expand–contract (parallel change) for a column rename `name` → `full_name`**
| Release | Database | Code |
|---|---|---|
| 1 (expand) | add `full_name` (nullable) | write **both** columns, read `name` |
| 2 (migrate) | backfill `full_name` in batches | read `full_name` (fall back to `name`), still write both |
| 3 (contract prep) | — | stop writing `name` |
| 4 (contract) | drop `name` | — |
At every step, the **previous release still works** with the current schema → safe rollback.

**Migration rules**
- Run migrations as a separate, idempotent step (job/init container) **before** the new code; one migration owner at a time (lock).
- Avoid long locks on big tables: create indexes **concurrently** (Postgres `CREATE INDEX CONCURRENTLY`), add columns without volatile defaults, backfill in batches, use online schema tools (gh-ost, pt-online-schema-change) for MySQL.
- **Never** in the same release as code that depends on it being finished: drops, renames, `NOT NULL` without default, type changes.
- Test migrations on a production-sized copy ([migration tests](../Testing%2C%20Reliability%20%26%20Observability/Backend-and-Distributed-System-Testing.md#3-database-integration-tests-transactions-and-migration-tests)).

**Rollback options**
- **Code:** redeploy the previous image digest (`kubectl rollout undo`, Argo Rollouts abort, CodeDeploy rollback) — fast if schema is compatible.
- **Feature flag:** turn it off — fastest.
- **Data:** usually **roll forward** with a corrective migration; restore from PITR only for disasters (data loss trade-off).
- **API compatibility:** additive changes, tolerant readers, versioned events — consumers and producers deploy independently ([contracts](../Testing%2C%20Reliability%20%26%20Observability/Backend-and-Distributed-System-Testing.md#1-api-contract-tests-schema-compatibility-and-consumer-driven-contracts)).

#### Modern C++ example — checking each release against the schema of its neighbours (can we roll back?)
```cpp
// g++ -std=c++20 main.cpp && ./a.out
#include <iostream>
#include <set>
#include <string>
#include <vector>

struct Release { std::string name; std::set<std::string> schema_after; std::set<std::string> code_reads, code_writes; };

bool compatible(const std::set<std::string>& schema, const Release& code) {
    for (auto& c : code.code_reads) if (!schema.count(c)) return false;
    for (auto& c : code.code_writes) if (!schema.count(c)) return false;
    return true;
}

void check(const std::string& title, const std::vector<Release>& rs) {
    std::cout << title << ":\n";
    for (std::size_t i = 1; i < rs.size(); ++i) {
        bool new_ok = compatible(rs[i].schema_after, rs[i]);
        bool rollback_ok = compatible(rs[i].schema_after, rs[i - 1]);        // previous code on the new schema
        std::cout << "  " << rs[i].name << ": new code " << (new_ok ? "ok" : "BROKEN") << ", rollback to " << rs[i - 1].name << ' '
                  << (rollback_ok ? "safe" : "UNSAFE (old code needs a column that is gone)") << '\n';
    }
}

int main() {
    std::vector<Release> big_bang{
        {"r0", {"id", "name"}, {"name"}, {"name"}},
        {"r1 rename in one step", {"id", "full_name"}, {"full_name"}, {"full_name"}},
    };
    std::vector<Release> expand_contract{
        {"r0", {"id", "name"}, {"name"}, {"name"}},
        {"r1 expand", {"id", "name", "full_name"}, {"name"}, {"name", "full_name"}},
        {"r2 migrate+read new", {"id", "name", "full_name"}, {"full_name"}, {"name", "full_name"}},
        {"r3 stop writing old", {"id", "name", "full_name"}, {"full_name"}, {"full_name"}},
        {"r4 contract", {"id", "full_name"}, {"full_name"}, {"full_name"}},
    };
    check("big-bang rename", big_bang);
    check("expand -> migrate -> contract", expand_contract);
}
```

**Output:**
```text
big-bang rename:
  r1 rename in one step: new code ok, rollback to r0 UNSAFE (old code needs a column that is gone)
expand -> migrate -> contract:
  r1 expand: new code ok, rollback to r0 safe
  r2 migrate+read new: new code ok, rollback to r1 expand safe
  r3 stop writing old: new code ok, rollback to r2 migrate+read new safe
  r4 contract: new code ok, rollback to r3 stop writing old safe
```

### Interview answer
"Fast rollback depends on backward compatibility, so every release must work with the schema and APIs of its neighbours. Schema changes go through expand, migrate and contract over several releases — add the new column, dual-write and backfill in batches, switch reads, stop old writes, and only then drop — so I can always redeploy the previous digest. Migrations are small, forward-only, run before the code by one runner with locking, avoid long table locks with concurrent index builds and online schema tools, and are tested on production-sized data. Feature flags are the fastest rollback; for bad data I usually roll forward with a corrective migration rather than restore."

## Cheat sheet

| Topic | Remember |
|---|---|
| CI vs. CD | integrate + test every change · deliver (one-click) or deploy (automatic) every passing change |
| Provenance | signed SLSA attestation (repo, commit, workflow, builder) via Sigstore; verify at admission |
| Pipeline security | actions pinned by SHA, minimal permissions, OIDC, protected branches/environments, ephemeral runners, no secrets to forks |
| Release strategies | rolling (cheap, mixed versions) · blue-green (instant switch, 2×) · canary (smallest blast radius, metrics) · flags (deploy ≠ release) |
| Progressive delivery | canary + automated analysis + auto-rollback (Argo Rollouts, Flagger) |
| Pipeline stages | fast checks → package once (signed, SBOM) → integration → staging → canary → 100% |
| Gates | tests, scans, coverage on changed code, reviews, migration checks, perf budgets |
| Build once | promote the same digest; config per environment |
| DORA | deployment frequency, lead time, change failure rate, time to restore |
| GitHub Actions | events → jobs (parallel, `needs`, matrix) → steps (`uses`/`run`); permissions; OIDC; environments; artifacts vs. cache; reusable workflows |
| Migrations | expand → migrate → contract; small, forward-only, before code; concurrent indexes, batched backfills |
| Rollbacks | flag off < redeploy previous digest < roll-forward fix < PITR restore |
